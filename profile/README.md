<p>号少的时候，什么都记得住；过了十个，就开始出问题：某天一个号被要求重新验证，你想回溯它前几天走了哪条线、访问过什么，却发现日志只留了错误信息，IP 和时间都没记。这篇不按概念讲，直接把过去一年遇到的几个真问题串起来：谁用了哪条线、出事能不能翻出记录、连坐怎么蔓延、记录留多久够用。每个问题后面都给具体做法，都是能当天落地的那种。</p>

<h2>一、第一个真问题：号多了，谁在用哪条线</h2>
<p>这个问题的典型症状是，你想给某个号换个环境，结果不敢动，因为不确定它现在挂在哪条线上。解决它只需要一张对照表，但很多人是靠记忆维持的，一旦有同事接手就断了。</p>
<h3>先用一张表管住归属关系</h3>
<p>我的做法是把对照表放进版本管理，字段就五个：账号标识、出口编号、归属城市、绑定日期、最后检查时间。每次改动都留一条提交记录，谁在什么时候把哪个号挪到了哪条线，一目了然。这不是什么高级方案，但比存在聊天记录里强太多。</p>
<h3>这张表要和谁对齐</h3>
<p>对照表不是给自己看的，要和负责采购的人、负责跑任务的人对齐。采购的人知道每条线的有效期，跑任务的人知道哪个号该走哪条线，三方看的是同一张表，才不会出现「线过期了还在用」这种事。</p>

<h2>二、第二个真问题：出事时能不能翻出当时的情况</h2>
<h3>只记错误信息是不够的</h3>
<p>常见的日志写法是「登录失败，状态码 403」，这条记录事后基本没用。你需要的是：什么时间、哪个账号、从哪个出口 IP 发出的请求、目标是谁、返回了什么。少了出口 IP，就无法判断是账号问题还是线路问题。</p>
<h3>至少要能按出口反查</h3>
<p>出问题时往往是「一批号同时异常」，这时候要按出口反查：这条出口上还挂了哪些号，它们最近有没有一起异常。如果日志只能按账号查，你就要一个个翻，效率极低。建索引时把出口 IP 作为可选维度，这个决定在后期能省几十个小时。</p>

<h2>三、第三个真问题：连坐是怎么从一条线蔓延开的</h2>
<p>连坐很少是一次性爆发，通常是渐进式的。第一步，某条出口因为高频请求被限速；第二步，挂在这条线上的几个号开始出现延迟升高；第三步，其中一个号触发验证，用户手动通过；第四步，验证频次上升，其他号也被牵连；第五步，整条线上的号一起出问题。等到第五步才动手，前面的记录早就断了。</p>

<h2>四、第四个真问题：记录留多久才算够</h2>
<p>太短没用，太长占空间还涉及隐私。我的经验是分层：请求级明细留七天，足够覆盖大多数事后追溯；每日汇总留九十天，用来观察趋势；出口变更记录长期保留，因为它体量小、价值高。这样既不爆盘，也不至于查不到。</p>
<p>如果业务涉及对外服务，还要考虑合规要求。有些行业要求访问日志保留六个月，具体以所属行业规定为准，别自己拍脑袋定。</p>

<h2>五、一次把四个问题解决掉的最小方案</h2>
<p>不需要上什么系统。一个 CSV 对照表加一份结构化日志就能跑起来。日志用 JSON 行格式，每行一条，字段固定，写到按天切分的文件里。查询用命令行工具过滤，比如按出口筛出当天的所有请求，或者按账号筛出最近的验证事件。跑顺了再考虑上数据库。</p>
<p>关键是三个约定：一是出口编号必须出现在每条日志里；二是任何换线动作都要在对照表里留痕；三是每周花十分钟看一眼失败率最高的那条线。这三条坚持一个月，你会发现排查问题的速度明显变快，也不会再出现「不知道谁动了什么」的僵局。</p>

<h2>常见问答</h2>
<h3>日志里记 IP 会不会有隐私问题？</h3>
<p>答：记录自己业务的访问日志属于常规运维，但要注意范围和期限。只记与运维相关的字段，不记录对话内容本身，按需设置保留期，并在内部说明用途。涉及个人信息的部分应按相关规定处理。</p>
<h3>小团队没精力维护日志怎么办？</h3>
<p>答：先把最小集跑起来，就三个字段：时间、账号、出口 IP。这三样写进现有日志里，成本几乎为零，却能解决八成回溯需求。等真遇到需要细分的时候再补字段。</p>
<h3>出口换了以后旧 IP 还要留档吗？</h3>
<p>答：要。旧 IP 是解释历史异常的关键线索。有过一次经历：某号被验证，查了半天没头绪，最后发现是三天前换过线，而旧线当时已经被标记。如果没留换线记录，这个结论根本得不到。</p>
<h3>怎么判断一条线是不是该整体停用？</h3>
<p>答：看聚合数据。同一条线上超过一半的号在三天内出现过异常，就值得整条停用，别一个个换。单号异常先单独处理，避免因为一个号的问题浪费一条好线。</p>
